## Profile and Resume Delivery

| Endpoint | Delivered behaviour |
|---|---|
| `GET /profile` | Returns only the authenticated user's structured pre-fill data and resume list |
| `PUT /profile` | Replaces the profile with normalized name, contact, education, experience, skills, and links |
| `POST /profile/resumes` | Validates and stores PDF, DOC, or DOCX metadata with a 5 MiB limit |
| `GET /profile/resumes` | Returns only the current user's resume metadata in stable order |

The development document defines resume storage as metadata for the MVP. The API therefore does not
accept or persist document bytes. It creates a private server-side storage key for later object-store
integration and never returns that key to the client. Tests reject path traversal, unsupported file
extensions, incorrect content types, and oversize documents.

## Application Delivery

| Endpoint | Delivered behaviour |
|---|---|
| `POST /jobs/{job_id}/applications` | Creates one manual draft or submitted record for the current user and job |
| `GET /applications` | Returns user-owned history with total and page counts |
| `GET /applications/{application_id}` | Returns one owned application with its full job record |
| `PATCH /applications/{application_id}` | Applies a valid lifecycle transition and rejects invalid transitions |

Applications follow an explicit state model. Draft can become submitted or withdrawn. Submitted can
become interviewing, rejected, or withdrawn. Interviewing can become offered, rejected, or
withdrawn. Offered can be withdrawn, while rejected and withdrawn are terminal. Repeating the
current state is idempotent. A unique user and job constraint prevents duplicate application
histories.

## Form Assistant Boundary

| Endpoint | Delivered behaviour |
|---|---|
| `GET /assistant/bootstrap` | Publishes contract versions, manual fallback, and available fixture forms |
| `GET /assistant/forms/{form_id}` | Returns the platform form schema used by the confirmation UI |
| `POST /assistant/map-fields` | Sends the form snapshot and minimized authenticated profile to an injected Member 4 service |
| `POST /assistant/applications` | Validates confirmations and atomically stores the submitted application and mapping evidence |
| `GET /assistant/mappings/{mapping_id}` | Returns an owned mapping record with mapping, confirmation, provider, prompt, and version evidence |

The mapping route contains no LLM logic. It depends on a typed gateway so Member 4 can connect the
provider and mapping implementation without changing HTTP or database code. Until that dependency is
registered, the route returns HTTP 503 and instructs the client to use manual entry. This implements
the agreed graceful degradation path.

Assistant persistence verifies that the form belongs to the selected job, every referenced field
exists in the stored form schema, and each required field was confirmed or replaced by an edited
value. The application and mapping record commit in one transaction, preserving the evidence needed
to reconstruct the user-controlled submission.

## Security and Privacy Controls

- Every profile, resume, application, and mapping query includes the authenticated user identifier.
- Another user's application or mapping returns HTTP 404, which does not reveal whether the record
  exists.
- Mapping receives a minimized profile containing only pre-fill fields and no account hash, token,
  internal storage key, or unrelated database identifiers.
- Resume filenames cannot contain paths, and private storage keys are generated by the server.
- Application status and assistant confirmation rules run before commit, so invalid requests do not
  leave partial records.
