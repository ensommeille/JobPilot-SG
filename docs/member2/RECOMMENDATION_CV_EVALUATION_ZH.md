# 推荐功能：基于简历的本地核验与改进（2026-10-20）

## 核验方法与隐私

只在本机读取提供的 PDF 以提炼测试要点；仓库、测试数据和 PR 不包含简历原文、姓名、联系方式或 PDF 文件。回归测试使用匿名的技术技能与虚构岗位。

## 发现的问题

1. 本机 `jobpilot` 数据库的现存资料只保存了一个技能标签 `Python`，教育、经历和个人介绍为空，也没有简历文件记录。它不能代表整份简历。当前产品的推荐功能本来就不解析上传的简历文件，只读取已保存的 `Skills` 标签。
2. 将简历中的 21 项明确列出的技术/数据工具用匿名标签在本机检测，旧的命名技能识别器只能认出 12 项；Pandas、NumPy、scikit-learn、Matplotlib、REST APIs、Linux、Spark、Hadoop、Kafka 被漏掉。即使用户手动保存了这些标签，相关岗位也可能被低估。
3. 原排序只看技能证据和新近程度，不利用已保存介绍或可用时间里明确的「寻找实习」意向。同等技能证据时，较新的全职岗位可能排在实习岗位之前。
4. 本机只有两条演示岗位，且没有可用的岗位要求提取记录。因此无法凭本机现有数据衡量真实岗位推荐的准确率；不能把无推荐误判为用户不合适。

## 改进与验证

- 补齐上述 9 项技能的命名识别，并让保守的「岗位要求 ↔ 个人技能」比较器支持这些以及简历里已有、此前不能形成明确对应的 Vue 3、MongoDB、Power BI、Data Analysis 等标签。不会从某一工具推断掌握相关工具，也不会把普通句子里的 *spark*、*pandas* 当成技能。
- 仅当保存的自我介绍或可用时间**明确且肯定**写出寻找/可参加实习时，在无明确技能缺口的候选中优先排列实习岗位；这不是硬过滤，也不是资格判断。过去的实习、否定表述或 PDF 文件本身不会触发此偏好。
- 推荐结果显示实际参与比较的不同命名技能数量，并明确指出简历文件不会被解析。这样用户能发现资料页只保存一个技能时的误差来源。
- 匿名回归场景验证了数据实习岗位可凭 Pandas、NumPy、Kafka 的明确证据排在仅有 Python、SQL 对应的岗位前面；另一场景验证了明确的实习意向在同等技能证据时改变排序。
- 后端全量测试 749 通过、1 跳过（本机缺少 Docker CLI）；推荐页面 10 项浏览器交互测试通过；前端构建与代码检查通过。

## 仍需团队处理

要对真实岗位给出可信的准确性结论，需要真实且仍有效的岗位要求提取数据，并由人核对推荐前后顺序。用户还需要在**正在使用的同一环境/账号**的资料页保存技能标签与实习意向；仅有本机 PDF 或简历文件元数据不会被推荐服务读取。入职日期、工签、学历等条件仍需人工核查，不能由技能重合推断。
